# LeaseDD V1：融资租赁尽职调查报告 Skill 完整整合方案

**版本：** 1.0（实施设计，不是已实现的软件）  
**核查日期：** 2026-09-18  
**目标环境：** 本地 Ubuntu、现有 Codex；以项目资料文件夹为输入，以固定框架的尽调报告及其证据、计算、复核记录为输出。

## 0. 决策摘要与核查边界

本方案保留已经确定的业务流程，但修正上一轮的“DocForge 作为可运行代码骨架”建议：**新建轻量 Python 项目 LeaseDD，以 DocForge 的章节组织思路为参考，而不是 Fork 其完整桌面应用；财务、证据和审核规则按照融资租赁业务独立实现。**

原因来自实际代码，而不是对 README 的功能描述：DocForge 的 PDF 解析只匹配少量文本指令并把结果返回为一页；其 Word builder 从段落新建文档，没有财务表格构建路径；credit-spread-portal 的部分公式把缺失项当零，指标口径也不能直接对应中国企业财务分析；BidMaster 的 GateKeeper 本身只判断审核标记文件是否存在。OpenBidKit 的模板字段处理有可借鉴的实质实现，但不适合作为整个本地 Skill 的运行依赖。[D3][D4][C1][B1][O2]

这不是“四个应用合并”，也不是重新开发四个应用。整合单位是**设计约束、数据契约、少量经许可和测试的函数，以及已有文档处理库**。

### 0.1 本次实际完成的核查

通过 GitHub 接口读取了四库的目录、关键依赖、部分许可证文本，以及与生成、解析、财务计算、审核闸门和 Word 模板直接相关的源码。逐文件范围、Git blob 指纹见 `02_源码核查与迁移矩阵.md` 和 `upstream_audit.json`。

本次属于**关键路径静态源码核查**：没有声称逐行审计所有文件，没有运行四套应用，没有验证其全部测试或真实文档处理效果。整库克隆在当前执行环境因网络解析失败，源码核查使用 GitHub 读取接口完成。因此交付包不包含四库源码，也不把 README 的测试数量当作通过证明。读取时使用默认分支，记录的是文件 blob 指纹；正式开工时仍须冻结真实 commit，不能拿 tree/blob SHA 冒充 commit。

### 0.2 四库的最终定位

| 仓库 | V1 定位 | 可以借鉴什么 | 不做什么 |
|---|---|---|---|
| DocForge | 章节任务与模板组织参考 | Section Context、章节独立生成/重写、模板树 | 不继承 Tauri/React；不采用现有 PDF parser、自由大纲和 Word builder |
| credit-spread-portal | 财务标准化与确定性计算参考 | 科目映射先规则后模型、计算与解释分离、校验结果留痕 | 不引入 Azure；不直接复制原指标口径和美国阈值；授权文本核实前不移植源码 |
| BidMaster-Pro | 阶段闸门与任务封装参考 | 分阶段执行、超时、审核记录、失败处理 | 不复制 AGPL 源码；不引入其整套 LangGraph/服务端框架 |
| OpenBidKit_Yibiao | 模板优先和字段校验参考 | 原模板副本、字段分类、结构校验、失败清理 | 不复制 AGPL 模板处理源码；不引入 Electron/.NET 桌面工具链 |

**V1 固定为：一个 Python 核心、一套事实模型、一条状态链、一个 Codex 写作入口、一套固定 Word 模板渲染路径。**

## 1. 产品目标、首期范围与非目标

### 1.1 核心交付

用户指定项目资料目录后，系统能够：盘点文件与缺口；提取和核对事实；标准化财务报表并计算指标；按既有《尽职调查报告》框架分配章节问题；将证据限定到每个问题；逐章撰写；校验数字、口径和前后表述；形成风险反向问询；输出待复核稿或经人工确认的定稿。

**自动化的是资料加工与文稿编制，不是现场真实性认定、法律效力判定或者替审批人作出决定。**报告可以形成审慎、保留或者否定意见，不能把“生成成功”定义为“项目可批准”。

### 1.2 V1 必须支持

支持本地 PDF、DOCX、XLSX、CSV、TXT/Markdown。扫描页或图片按需进入独立解析适配器；旧 `.doc`、加密文件及暂不支持的格式必须进入清单，输出“待转换/需授权解密/不支持”，不得静默跳过。

支持同一项目多个主体及角色：承租人、联合承租人、保证人、供应商等；共享基础 Entity/Fact 模型，不为不同角色各维护一份相互矛盾的公司事实。支持近年及最新一期报表，实际期间由资料决定，不硬编码“必有三年完整数据”。

支持从同一事实版本生成报告、风险问询清单和来源对照表。首期不另做授信系统、客户管理系统或者审批流平台。

### 1.3 V1 明确不做

不建设 WebUI、桌面壳、多人在线编辑、移动端；不把 PostgreSQL、Redis、Celery、MinIO、Azure、LangGraph 或向量数据库作为必需服务；不强制配置新的模型 API Key；不建设全市场公告采集平台；不建立未经校准的自动信用评分与批准模型。

外部研究先支持**经授权导入的公告、网页快照及来源清单**。现有下载脚本经核查后可以作为外部资料供应端，不能为了本项目重建一套采集平台。实时网络研究作为显式可选阶段，不与敏感资料上传权限混为一谈。

## 2. 源码核查对设计的直接影响

### 2.1 DocForge：参考章节设计，替换事实入口与出口

`src/lib/pipeline/generator.ts` 将章节、检索段落、已生成章节和用户要求拼接成提示词，输出字符串；适合作为“每章单独生成”的思路参考，但没有持久化 Claim/Evidence 的约束。其参考编号在当前章节重新编号，不能直接作为跨章节证据 ID。[D2]

`src/lib/pipeline/analyzer.ts` 让模型生成目录；解析失败时回退为 `1. Overview` 等最小结构。这种回退不能进入 LeaseDD：原框架解析失败必须报错或进入待确认，不能生成看起来成功的通用报告。[D5]

`src/lib/knowledge/parser/pdf-parser.ts` 将文件字节按 UTF-8 解码，正则匹配 `BT/ET` 和 `Tj`，返回 `pages: [readable]`。不能作为中文年报、多页表格及来源页码的正式解析路径。[D3]

`src/lib/document/builder.ts` 使用段落、标题、页眉页脚等新建 DOCX；其正文解析只处理普通段落和列表，并未提供财务表格装配。它也不是保留既有 Word 模板的填充器。[D4]

**落地变化：** 借鉴章节上下文和模板树；自行定义严格 SectionContract；使用成熟文档解析库和模板填充库，不把这些不满足需求的实现整体迁入。

### 2.2 credit-spread-portal：借鉴计算架构，不照搬口径

`tools/ratio_calculator.py` 确实将计算与模型写作分开；但其中部分字段用 `or 0` 补值；`debt_to_assets` 是短期债务与长期债务之和除以资产；ROA/ROE 使用期末数；部分周转指标固定乘 365；缺少可比值时趋势可能返回 stable。[C1]

这些不代表该库所有计算都错误，而是说明：**程序计算也必须先定义准确的业务口径。**缺失存货不等于存货为零；借款口径的债务率不等于总负债口径的资产负债率；半年数据不能按全年经营流量解释。

`tools/chart_of_accounts.py` 的规则说明及已读规则主要针对英文科目；`tools/schema_loader.py` 即使名字通用，也直接导入 Azure Content Understanding 对象。[C2][C3]

`agents/validation_agent.py` 将规则执行、模型解释与 case 状态保存串联；存在 flags 仍会发出 validation_complete，由后续人工审核处理。LeaseDD 采用更明确的三维状态，避免把执行完成当成财务检查通过。[C4]

**落地变化：** 中文科目、原框架公式、期间规则、空值语义和证明链均独立实现；不移植 Azure Agent 外壳。

### 2.3 BidMaster：审核标记升级为绑定输入的审核记录

`core/agent_engine/gate_keeper.py` 的 `is_passed()` 仅检查 `.reviewed` 文件是否存在；记录包含阶段、审核人、时间与说明，但该类不把输入数据摘要纳入检查。[B1]

`orchestrator.py` 有阶段、条件路由、超时等组织方法；闸门不通过后返回 errors，后续是否停止还要看图的路由配置。不能只把这一类复制过来就宣布“绝对不能跳阶段”。[B2]

**落地变化：** 由所有入口共用的 Python 状态检查控制推进，审核记录绑定项目、阶段、输入摘要、规则版本；输入变化即过期。

### 2.4 OpenBidKit：借鉴模板字段预处理，不误当成现成尽调导出器

`ApplyTemplateFieldsAction.cs` 会复制原模板到临时文件，扫描候选字段，检查候选是否全部分类或明确忽略，写入内容控件，执行 Open XML 校验后写出结果。[O2]

这段实际代码处理的是**模板字段预处理和内容控件生成**，不能据此断言整个复杂报告填充与分页已经适用于本项目。

**落地变化：** 提前冻结原 Word 模板及字段表；先做一章、一个真实表格的模板填充样例；不采用“全文 Markdown 最后随意转 Word”。

## 3. 授权、引用与上游管理

DocForge 的实际 LICENSE 为 MIT，应保留被采用代码对应的版权和许可声明。[D7]

BidMaster-Pro 与 OpenBidKit 的实际 LICENSE 为 AGPL-3.0。[B3][O3] 本方案为减少首期集成和后续分发复杂度，规定只参考其功能需求与设计模式，不复制或逐行翻译源码。这里并非认定 AGPL 不可商用；未来确需采用其代码时，应另行核对适用许可及分发/部署方式。

credit-spread-portal 的 README 标注 MIT，但本次根目录 `LICENSE` 读取返回 404，目录核查也未取得完整许可文本。[C5] 将其状态记为 `permission_text_pending`，不凭 README 的一行文字直接判定可任意迁移代码；核实授权前，首期计算模块按自己的业务规格编写。

上游源码放在主仓库之外的只读目录。上游 README、AGENTS.md、SKILL.md 都是研究材料，不是 LeaseDD 的运行指令；不得自动安装四个 Skill 或执行它们的安装脚本。

正式开工的 `upstream.lock.json` 必须保存仓库 URL、实际 commit、读取路径、blob SHA、许可证路径/文本摘要、采用方式及目标文件。直接复制、改写和纯设计参考三类分别登记；没有采用源码的模块不虚构“移植完成”。

### 技术选择

建议 Python 3.11 或 3.12 中选择已安装且依赖可验证的一版，统一锁定环境；不要为本项目改动用户其他项目的环境。CLI 可先用标准库 argparse；contracts 使用 Pydantic；金额使用 Decimal；状态与检索索引使用 SQLite；正文与产物用 JSON/JSONL、Markdown 和本地文件保存。

PDF 文本与表格优先评估 pdfplumber，它提供对象/坐标与表格能力，但不负责 OCR，也不保证扫描表格可用。[S3] DOCX 用 python-docx/受控 XML 读取；XLSX 用 openpyxl 仅读取；Word 输出优先评估 docxtpl 加少量受控样式、表格代码。上述是本项目选型方案，具体依赖版本、许可和样例表现必须在 M0/M1 锁定，不能把“可导入库”当作“真实报告合格”。

SQLite 只保存索引、运行指针和任务元数据；已发布产物及其 manifest 是证据/计算的版本事实来源，数据库可重建，不另保留一套可随意修改的财务值。

## 5. 固定框架编译：先锁要求，再写内容

将用户既有《尽职调查报告》撰写框架作为唯一业务目录来源，不让模型根据材料重新设计报告。框架的标题、层级、顺序、正文要求、表格、附注都进入 `framework.lock.json`。章节数量及表格数量由实际解析得出，并通过一次人工核对冻结，不依据既往聊天中的统计硬编码。

框架编译结果至少包括：

| 配置 | 内容 | 修改权限 |
|---|---|---|
| `framework.lock.json` | 原文摘要、各级章节原文、排序、稳定 section_id | 需显式升级框架版本 |
| `questions.yaml` | 每章必须回答的问题、必要事实、证据要求、缺口写法 | 框架维护，不由写作任务自行改 |
| `formulas.yaml` | 指标定义、输入口径、公式函数、期间规则、显示精度 | 业务口径确认后版本化 |
| `materials.yaml` | 不同交易类型/主体角色的材料要求及可替代证据 | 规则维护 |
| `field_map.json` | 章节/表格与 Word 模板插槽的对应关系 | 模板维护 |

“原框架出现两种可选公式”“旧科目与新科目口径不一致”“Word 编号与框架文字不一致”等情况应形成 `spec_issues.json`。未确认的歧义不交给模型随机选；该指标可先显示“口径待确认”，其他已明确部分继续生成待复核稿。

每次报告运行冻结 `framework_hash + formula_version + template_hash`。报告章节的内容可更新，标题和表格结构不随模型改变。公司类型/交易类型不同，只改变章节内问题是否适用及材料要求，不擅自删改强制章节；不适用须说明理由。

## 6. 数据契约与事实层

### 6.1 单一模型来源

在 `contracts/` 维护 Pydantic 模型，再导出 JSON Schema；不要人工并行维护两套定义。字段新增和语义变更通过 schema_version 迁移。金额采用十进制字符串序列化，不能先转二进制浮点再转回 Decimal。

### 6.2 核心对象

| 对象 | 最少字段 | 关键约束 |
|---|---|---|
| ProjectSpec | project_id、report_as_of、主体角色、交易类型、框架/模板版本、数据使用策略 | 主体、日期、许可范围明确 |
| SourceDocument | doc_id、SHA256、原路径、来源类型、发布日、资料时点、保密级别、解析状态 | 同名不等于同文件，原件不覆盖 |
| EvidenceSpan | evidence_id、doc_id、定位器、原文或表格片段、解析版本 | 定位器可回到原件，不能虚构页码 |
| Entity | entity_id、名称、统一代码/证券代码、别名、角色 | 联合承租人与保证人分别建主体 |
| Observation | 原始值、原文科目、单位/币种/期间候选、来源、提取方式 | 原始观察不可被标准化过程覆盖 |
| Fact | concept_id、entity_id、scope、period、normalized_value、币种、来源集合、状态 | 与原始观察关联；缺失不是零 |
| FactSelection | 同一事实键的候选、采用项、冲突、原因、复核记录 | 不自动删除相互矛盾的来源 |
| MetricResult | metric_id、formula_version、input_fact_ids、结果、状态、期间、显示方式 | 结果来源和口径可复算 |
| SectionContract | section_id、原题、问题、事实/指标/表格槽、证据要求 | 不接受自由新增或缺失章 |
| SectionDraft | 问题答复、段落块、事实/指标引用、表格绑定、缺口 | 模型提交候选，不能直接成为定稿 |
| Claim | 陈述文本、事实/推断/管理层说法类型、支持与反证、涉及段落 | 证据存在不等于证据支持该结论 |
| CheckIssue | rule_id、对象、严重性、预期/实际、状态、处理记录 | 不能仅靠删掉提示让检查通过 |
| ReviewRecord | 审核对象、输入摘要、人工决定、真实审核标识、时间 | 与当前版本绑定，不用模型伪造人审 |
| ArtifactManifest | run_id、输入输出摘要、代码/规则/模型任务版本、状态 | 成功产物可追溯、过期可检测 |

具体示例见 `05_数据契约与命令接口.md`。其中示例是设计样例，不是用户项目实际数据，也不是已经编译出来的生产 Schema。

### 6.3 一个财务数字的完整身份

一个数字至少由“主体 + 报表范围 + 科目 + 期间类型与日期 + 币种 + 数据版本”共同识别。

例如，同一公司同日的合并货币资金和母公司货币资金是不同事实；2026 年上半年收入和 2026 年第二季度收入也是不同事实。公开披露、企业盖章报表、管理层口头说明是不同来源性质，不能无条件相互替换。

对于文本值也保留出处和时间。管理层说“订单将明显增长”只能形成管理层预期或预测假设，不能形成已实现的订单或收入。

### 6.4 来源定位

PDF 保存物理页序（从 0 开始）及可选印刷页码标签；坐标仅在解析器真实提供时保存，并记录坐标系。DOCX 用段落索引、表格/行/列定位，不伪造稳定页码。XLSX 用工作表名、单元格地址；文本用行号/字符范围；网页快照用 URL、抓取时间、正文摘要和原始快照。

同一 Evidence 可以支撑多个事实；同一事实也可能来自多个 Evidence。低提取置信度只是识别不确定性，不代表企业信用不好；高提取置信度也不代表材料真实。

## 7. 文档接入、盘点与提取

### 7.1 盘点

扫描授权目录，计算摘要，识别同内容不同文件名和同名不同版本；建立来源、主体、期间、资料类别候选。档案清单应覆盖全部文件，包括失败、加密、空白、重复及不支持项。

先按交易类型检查材料是否存在，再检查覆盖期间和主体。缺口清单区分：完全缺失、过期、格式不可读、事实冲突、存在文件但不支持所需结论。建议补充的材料进入独立任务清单，不得写成“已取得”。

### 7.2 分格式处理

| 格式 | V1 路径 | 失败处理 |
|---|---|---|
| 文字型 PDF | 按页取文本、表格、表头及坐标；保留跨页续表关系 | 标记异常页，进入人工或可选解析适配器 |
| 扫描 PDF/图片 | 先检测，再按需调用已授权本地识别适配器 | 保留原图和识别状态；不虚构识别成功 |
| DOCX | 保留标题、段落、表格结构与定位器 | 暂不支持的特殊对象列入缺口 |
| XLSX | 读取工作表、值/公式/缓存、单位和单元格定位 | 不运行宏；缺少公式缓存记为无法取得值 |
| CSV/TXT/MD | 编码检测、结构化行号、CSV 类型与单位检查 | 不能把乱码当正常材料 |
| DOC/加密/压缩包 | 登记后受控转换、解密或解包 | 无授权/工具则 pending，不静默忽略 |

XLSX 解析不能靠执行任意公式或宏“修复”资料；原公式、缓存值和确定性重算值分开保存。扫描识别也不是本项目默认全量步骤。

### 7.3 事实提取及映射

规则优先处理明显字段、表头、日期、单位和常见中文科目。模型处理复杂叙述与少量歧义映射，但必须返回原文、候选值和来源引用，由程序校验后进入候选事实。

同一张表的单位与期间可通过显式继承记录传到单元格，不允许凭模型常识猜“单位应该是万元”。合并表与母公司表以结构和标题识别，不能只按出现顺序取第一张。

重复科目行不得简单求和。总计与明细建立 parent/component 关系，避免“短期借款 + 一年内到期长期借款 + 已包含它的借款合计”重复计入。

## 8. 财务计算与校验

### 8.1 不让 LLM 算数字的确切含义

原表披露数值由提取和复核确定；允许重算的合计、勾稽、比例和变化额由程序完成。**程序也不能从不完整材料中编造三张报表。** 报告同时保存 reported_value 与 calculated_value，二者有差异时列明原因，不自动拿重算值覆盖披露值。

### 8.2 指标规则

下面是待编入版本化公式表的设计口径，最终受原框架确认版本约束；不是未经确认强制替换原报告的公式。

| 指标/检查 | 本方案的约束 |
|---|---|
| 资产负债率 | 使用总负债/总资产；与有息负债率分开 |
| 流动比率 | 流动资产/流动负债；任何输入缺失则 unavailable |
| 速动比率 | 原框架公式所需科目必须齐全；缺失存货不当成零 |
| 现金比率 | 是否包括交易性金融资产、是否剔除受限部分，以冻结口径明确 |
| 毛利率 | 收入与成本必须同主体、同口径、同期间 |
| 净利率/归母/扣非 | 分开命名，不能用其中一个冒充另一个 |
| ROA/ROE | 期末数或平均数以确认口径确定；缺少期初数不能悄悄改公式 |
| 周转率/周转天数 | 期间、余额平均方式、年化及天数约定显式配置；不能半年流量默认按全年 |
| 有息负债 | 明细构成版本化，区分租赁负债/一年内到期部分，防重复 |
| 偿债覆盖 | 明确可用于偿债现金与本息支出的口径；缺债务计划不编 DSCR |
| 变化率 | 可比期间才计算；零或负基数需专门表达，不能机械解释增长率 |
| 趋势 | 无可比数据返回不可判断，不返回 stable |

### 8.3 勾稽

按适用报表结构检查资产=负债+权益，流动/非流动合计，收入成本及利润层级，现金流量与现金等价物变动等。现金流勾稽应纳入资料中适用的汇率变动影响；现金等价物口径不能无说明直接等同于资产负债表货币资金。

净利润不能机械等同于未分配利润变动；分红、期初调整等桥接项需要按资料解释。勾稽容差按披露精度和合计项目推导，不直接照搬统一百分比阈值掩盖金额差异。

### 8.4 数值语义

所有金额在内部保持 Decimal，仅展示层舍入；汇率换算是独立计算且需要来源。区分 `missing`、`not_disclosed`、`not_applicable`、`conflicted`、`zero_denominator`、`invalid_period` 等状态。显示“—”时必须可追溯原因，不把它改为 0。

不采用上游美国 mid-market 的 good/warn/fail 阈值作为公司审批政策；指标事实与风险判断分别存储。首期不做“分数大于某值自动批准”。

### 8.5 租赁分析扩展

交易结构保存金额、期限、付款/起租日、租金计划、保证金、费用、购买价/账面价/评估价、产权资料、担保条件及对应来源。已执行条款、拟议条款和压力情景假设分开。

需要计算租金及偿债计划时，必须具备约定的计息方式和还款规则；首期只实现明确选定的模式并配测试，其余返回 unsupported，不用等额本息替代任意合同。预测现金流与历史现金流分层；保证金、费用及其他债务不能重复算成可用偿债现金或重复扣减。

## 9. 证据包、章节生成与 Codex 接口

### 9.1 检索单位是问题，不是整份报告

每一条 SectionContract 中的问题先绑定需要的事实与指标，再检索解释材料。数字主要通过事实键精确检索；经营描述再用主体、期间、标题、关键词和原文段落检索。V1 不强制语义向量服务，后续确有召回不足才增加经过评估的检索模块。

证据包必须包含支持材料、冲突/反证、缺口、禁止越界的表述，以及其 hash。不能只给有利材料。已写章节只能提供摘要/风格和已确认结论列表，不能作为替代原始资料的事实来源。

### 9.2 章节输出约束

模型输出结构化候选，而不是直接覆盖最终 Word。段落中金额、比例、日期等采用 fact_ref/metric_ref 绑定，由程序形成最终显示文本；解释性文字也必须关联事实或者标明推断依据。表格内容全部由事实/计算数据生成，模型不手打整张财务表。

每个问题的答复状态是 answered、partial、gap 或 not_applicable。**问题已处理率**与**证据已满足率**分开显示，不能用“已写明资料不足”冒充“材料齐全”。

### 9.3 V1 不再开发一个嵌套模型平台

首期采用文件式任务适配器：

```text
Python next-task 生成 task.json + response.schema.json + evidence-pack.json
   → 当前 Codex 会话读取授权任务
   → Codex 只写 response.json 候选
   → Python import-result 做 Schema/来源/数字/覆盖检查
   → 合格候选进入下一状态；不合格则给具体错误并有限重试
```

这些命令是本方案拟开发的接口，不是四库已有能力。由现有 Codex 会话完成提取候选、写作和反向问询；Python 负责确定性步骤，不读取或挪用 Codex 登录凭据，不递归启动另一个 Codex，不假定能免费调用额外模型 API。

每个任务限定输入摘要、可读资料、输出位置、响应 Schema、重试次数和依赖。重试仍失败则 `waiting_review`/`failed`，保留已有成果和错误，不回退到通用报告或凭空填值。

## 10. 状态机、闸门与人工复核

### 10.1 三种状态必须独立

`execution_state` 表示程序是否运行完；`quality_state` 表示数据/引用是否满足规则；`review_state` 表示人工是否认可该版本。技术完成可以同时伴随资料缺口和人工未审核。

### 10.2 闸门设计

| Gate | 要检查的内容 | 缺口处理 |
|---|---|---|
| G0 基线 | 原框架/模板可识别；版本、授权、项目范围明确 | 无生产模板可跑合成测试，不冒充生产报告 |
| G1 文件 | 所有输入都有处理状态；来源和保密策略已登记 | 存在缺失/失败可继续，但进入缺口清单 |
| G2 事实 | 主体、期间、单位、来源可识别；冲突未被隐藏 | 不明的关键事实不能进入正式计算 |
| G3 计算 | 公式、输入、勾稽和可比期间检查完成 | 不可算指标留空并解释；不合格数值不传播 |
| G4 章节 | 原框架章节覆盖；问题有状态；引用有效；数字与事实一致 | 可生成明确标缺口的待复核章节 |
| G5 综合检查 | 前后口径一致；重大反证/风险已披露；无编造现场核查 | 未解决的无证据肯定结论必须修改或阻断 |
| G6 发布 | 模板字段/Word 结构合格；版本有效；人工确认 | 未人工确认只能导出待复核稿 |

定稿并不要求项目本身“没有风险”，而是要求报告没有隐瞒重要限制、没有把未核实事实当已核实事实，且获得对该版本的人工确认。反向问询也不能通过自动改写把问题一律“解决”。

### 10.3 审核和绕过风险

ReviewRecord 绑定 `project_id + object_id + input_hash + ruleset_hash + decision`。摘要变化即标记 stale，不继续沿用旧批准状态。所有命令通过同一服务层检查闸门，不能另留一个可绕过的 direct-render-final 路径。

自然语言“禁止跳过”不是权限控制。生产使用中，Agent 的写作环境不应拥有改正式程序、原始资料和人工确认记录的权限；用只读挂载/独立目录权限或操作员在 Agent 之外确认。若仍使用同一高权限账号运行全部工作，必须明确这只是防误操作流程，不是安全隔离，不能宣称模型绝对无法伪造人审。

报告发布确认与融资业务审批是两回事；系统不得伪造签名、盖章、现场访问或询证结果。

## 11. 全文校验与风险反向问询

### 11.1 确定性检查

检查主体名称和角色、期间、币种/单位、引用值、表格合计、金额/期限/利率/保证金一致性、编号和框架覆盖、重复段落、悬空引用、已过期输入，以及缺口是否被正文隐藏。

建立 Claim—Evidence 校验：程序可以检查引用确实存在、定位有效和数值一致；语义上是否真正支持该结论，还需模型辅助与人工抽查，不能把有 citation 等同于真实。

### 11.2 双向风险核查

以风险问题为中心形成四段：**质疑 → 已有证据能够解释的部分 → 仍然无法解释的部分 → 对判断的影响。** 业务答复与风险质疑读取同一事实版本，不允许业务答复悄悄新增未经验证的事实。

问询优先围绕资金用途、首要还款来源、经营与财务的相互印证、担保/抵质押与剩余风险、租赁物真实性及权属、联合承租责任和关联关系。具体法律适用应由相应授权资料或专业复核支持，不能让模型臆造监管规定。

例如，“未来订单改善足够覆盖租金”必须拆成已签订单、执行与回款条件、毛利/现金流假设和压力情景；没有依据不能直接写“还款有保障”。“已完成现场核实”必须对应真实核查记录，不能由两次模型一致回答替代。

输出 `risk_questions.md`、`risk_response_matrix.json` 与 `remaining_risks.md`，不把所有补件建议机械拼成“放款前应取得”的兜底条件。是否写进正式报告及采用何种表述，服从模板和本次任务要求。

## 12. Word 模板、字段与版式

### 12.1 双重固定

固定的不只是章节目录，还包括原 Word 模板中的纸张、页边距、段落样式、编号定义、表格宽度、边框、页眉页脚与目录字段。原模板保存只读副本；制作填充版本后形成字段清单并确认。

docxtpl 适合从已有 DOCX 模板和上下文生成文件，但标签不能随意跨 run、段落或表格行，RichText 等路径也需要显式样式控制。必须先检查模板标签，再用样例验证，不能默认“套了库就不丢格式”。[S2]

### 12.2 V1 实现方式

简单字段使用模板变量；多段落内容通过受控块插槽生成；财务表格使用固定列定义和数据行。首期不做自动猜测任意 Word 的所有可填位置，不做复杂模板可视化编辑器。

标题只由框架生成，模型不能在正文再加一层相同标题。编号由选定 profile 统一控制，不在模型正文里反复拼“一、”“1.1.”。表格按已确认模板配置处理；需要无底色时明确设置，不能依赖随机继承。

附带来源可采用正文中简洁编号、内部审阅版来源注释或单独来源对照表。无论对外显示哪种形式，内部 claim/evidence 对应都必须保留。

### 12.3 验收方式

程序检查无残留占位符、标题/表格数量与字段映射一致、无缺失引用、表格结构可读、指定样式和页眉页脚存在。对 XML 只做已定义的结构/样式检查；若未接入完整 Open XML Schema 校验器，不得把普通 XML 能解析说成完整规范验证通过。

在目标 Word/WPS 环境检查打开无需修复，长表分页、重复表头、标题跟随、目录更新、字体替代情况可接受。参考渲染器的预览不等于目标 Word 的绝对分页一致。**不承诺不同系统、字体和软件版本的页数完全相同。** 保留目标软件、字体名称与版本环境记录；不在项目包内分发未经许可的字体文件。

## 13. 增量更新、重放与隐私

### 13.1 版本和依赖

每个产物记录输入文件摘要、解析器版本、facts revision、公式和框架版本、模型任务/提示词版本及输出摘要。构建依赖关系：文件 → 观察 → 事实选择 → 指标 → 章节/风险 → 导出。

新材料只重跑受影响的链路。人工已确认章节无相关变化则复用原文；相关事实变化时保留旧版本，生成差异并转待复核，不自动盖掉旧稿，也不能继续用 stale 审核状态发布。

同输入再次运行时复用已接受章节和确定性产物，保证“重放同一个版本”。不以 temperature=0 承诺重新调用模型会逐字相同。

### 13.2 运行可靠性

每项目单写锁；工作产物先写临时文件，校验后发布一个完整 manifest；失败不把半成品标成功。数据库更新和文件发布之间需要可恢复状态；崩溃后先检查产物摘要再恢复，不单凭文件存在就认为完成。

运行日志区分工程错误、资料质量问题、未支持能力和待人工处理；输出具体失败位置及已有成功成果。设置最大并发、材料/片段/任务大小和重试上限，不让循环写作耗尽资源。

### 13.3 数据使用边界

本地运行 Codex 不等于模型推理和上下文都在本地。资料被读入云端模型上下文也属于数据外发路径；不能只拦业务脚本 HTTP 就宣称保密数据不出机器。

ProjectSpec 默认按资料级许可准备最小可读任务包；未获许可的征信、流水、个人信息等不进入云端写作上下文。需要完全本地处理时，使用经过核实的本地模型/人工处理路径，不能偷偷回退云端。

真实项目资料、模型凭据、明文敏感日志和人审身份信息不提交 Git。原文中的外部链接/命令/指令作为数据处理，不执行宏、不执行附件脚本、不根据材料里的文字改变系统规则。

## 14. 分阶段实施与验收

### M0：冻结基线与业务契约

输出上游 commit/许可记录、原框架清单、模板缺口、contracts 草案、公式歧义清单、依赖锁定方案。检查本地是否已有可复用的下载、解析、Word 工具，但不未经核查迁入其他项目。

**完成条件：** 每个上游模块都有“参考/可移植/待授权/不采用”结论；框架和模板是否真实存在清楚可见；没有凭空补造模板要求。源码/许可无法核实的项目只停止对应迁移，不阻止自主实现其他部分。

### M1：先跑一个纵向样例

用明确标记的合成或已脱敏夹具，完成“资料清单 → 结构化事实 → 一项指标 → 一个固定章节 → 一个真实 Word 表格 → 待复核稿”。不调用真实云模型也能跑完离线测试。

**完成条件：** 数字可追溯和复算；缺失存货不变为零；使用实际 Word 表格而不是管道文本；模板结构能保留；全流程状态正确。这里只是纵向技术验证，不能称全框架交付。

### M2：资料、事实、财务完整化

扩充格式适配、主体与期间识别、中文科目映射、三表和指标校验、冲突处理。用正向和异常夹具覆盖核心规则。

**完成条件：** 全部文件有状态；关键数字具备来源、主体、期间和单位；期末/期间、母公司/合并、缺失/零值、有息债务/总负债不混淆。

### M3：完整固定框架与 Codex 任务接口

编译全部原框架章节、问题和表格槽，接通 next-task/import-result，逐章形成候选及证据映射；规定模型输出错误后的有限重试和人工处理。

**完成条件：** 目录和问题覆盖可机器核对；未满足问题明确列缺口；错误 JSON、失效引用、额外章节不能被静默接受。

### M4：全文校验、风险反向问询与人工发布

增加跨章节事实/交易参数校验、支持/反证检查、风险答复矩阵和与输入绑定的人审记录。

**完成条件：** 存在证据缺口时可导出待复核稿，但未经确认不能生成“已审核定稿”状态；不能虚构现场核查；人工报告发布不等同业务批准。

### M5：回归、增量更新和真实材料验收

采用三类基准项目：上市公司公告为主；非上市企业且内外账/说明并存；联合承租与保证人多主体。可以先用脱敏/合成材料，再在授权环境使用真实项目复核。

**完成条件：** 重放版本不变；补一份资料只影响依赖章节；相关旧审核自动失效；用户目标 Word 环境打开正常；原件摘要不变；得到真实审核人员对至少一个完整报告版本的确认。

WebUI、多用户、更多租金模型、更复杂 OCR/检索、自动公告获取、其他报告类型均为后续阶段，不列作 V1 必须完成项。

## 15. 最小验收清单

| 类别 | 必须通过的用例/检查 |
|---|---|
| 材料盘点 | 目录中所有文件，包括坏文件、重复和不支持项均有状态 |
| 来源 | 导出使用的财务事实均带原件定位、主体、期间、单位；人工修订保留证据 |
| 空值 | 缺失存货/借款/现金等不补零；零分母和不适用有原因 |
| 科目口径 | 总负债率与有息负债率分开；明细和总计不重复叠加 |
| 期间 | 半年/全年不直接比较经营流量；累计值与单季值分开 |
| 主体 | 母公司、合并、承租人、保证人不混用 |
| 计算 | 公式版本、输入 ID、结果与舍入规则能离线复算 |
| 冲突 | 同事实不同值保留双方；不自动采最新文件覆盖旧事实 |
| 章节 | 与原框架标题、顺序、问题及表格槽逐项对照；缺口不是漏章 |
| 引用 | 悬空引用不能通过；语义支持度有人工抽查，不以形式检查替代 |
| 风险 | 正反证都进入问询；拟议措施不变成已落实措施 |
| 闸门 | 执行完成不等于质量通过；旧输入审核无法用于新输入 |
| 重跑 | 无关章节不改；有关章节出差异、旧版本保留 |
| Word | 无残留标签；财务数据是真实表格；目标软件打开无需修复；版式人工检查 |
| 原件 | 全流程结束原始文件 SHA256 不变 |
| 安全 | 路径逃逸、恶意指令、宏、未授权外发及日志泄密测试 |
| 失败恢复 | 中断恢复不产生重复正式产物，不把半成品发布成功 |
| 交付诚实性 | mock/synthetic/dry-run 标识存在；测试数量与结果来自实际运行 |

不设没有数据基础的“自动抽取准确率 99%”承诺。自动化验收针对结构、计算、引用可达和状态行为；内容真实性、语义充分性和审批判断保留人工核查。

## 16. Codex 的实施纪律与交付件

每个阶段一个明确变更集，交付变更文件列表、采用/新增模块清单、测试命令与真实结果、运行产物路径、未解决问题、下一阶段边界。不得靠删失败测试、放宽 Schema、给缺失值补零或伪造成功状态完成验收。

开发期间可改正式代码；实际写作运行使用冻结版本，不能边写报告边改变公式、闸门或模板以绕过检查。上游参考仓库不修改、不 merge；禁止“先把四库都跑起来”作为前置任务。

具体首轮任务书见 `03_Codex首轮实施指令.md`，该任务只覆盖 M0 与 M1，后续阶段按本方案逐项推进，防止一次无限扩展。

最终 V1 的每个项目至少输出：

```text

material_gaps.md
observations.jsonl
facts.jsonl
fact_selections.jsonl
financial_statements.json
financial_metrics.json
financial_checks.json
evidence_matrix.jsonl

consistency_checks.json
risk_questions.md
risk_response_matrix.json
review_records.jsonl
source_index.md
report_review.docx
artifact_manifest.json
```

经合法的人工作业流程确认后另发布定稿及对应 manifest；未确认时不生成伪装定稿。

**最终路线：先固定原框架和 Word 模板，再打通事实—计算—章节的纵向样例；以此扩展完整流程。不是四库拼接，也不是只写一份长 Prompt。**
