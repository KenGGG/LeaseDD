# LeaseDD M2 三张财务报表准确还原设计

## 目标

本阶段只提高资产负债表、利润表和现金流量表的还原准确性。固定处理链路为：上传 PDF → MinerU 转 Markdown → Agnes 理解三张表 → Python 按坐标核对来源 → 七条财务恒等式报警 → 必要时每张逻辑表最多复查一次。

准确性以原 PDF 为准。Markdown 来源校验只证明结构化结果与 MinerU 转换文本一致，不能代替人工 PDF 抽查。企业预警通仅保留为界面参考，不参与补值、纠错或公式计算。

本阶段不扩充指标，不建设完整附注、人工纠错平台、批次审批、复杂规则、正式报告或新 benchmark 平台，不新增 `financial_revision`，也不自动重跑已上传的真实材料。

## 现状与增量策略

现有系统已经具备 MinerU/MarkItDown 转换、物理表地图、Agnes map/interpret/extract 三阶段调用、单元格坐标校验、识别批次、共享限流和断点缓存。现有实现只覆盖四条恒等式；公式冲突会把已通过来源校验的数值清空；容差为固定单位比例；非金额列、完整期间证据和定向复查的表达不足。

本设计保留现有架构并收紧边界：Agnes 只负责理解和提出候选；Python 始终从 Markdown 坐标读取原值并独立验证；公式检查成为不修改数值的独立诊断层；现有识别批次保存所有结果和一次复查记录。

## 数据模型与 Agnes 契约

### 表和金额列

每张逻辑表必须返回：

- `statement_type`：三张主表之一。
- `entity`：原文公司主体。
- `scope`：`consolidated`、`parent`、`standalone` 或 `unknown`。
- `currency` 与 `raw_unit`，以及逐字原文证据。
- 每个金额列的 `block_id`、绝对 `column`、`label_column`、全部 `header_rows`、`raw_header`、完整 `period`、`period_kind`、`period_basis` 和期间证据。

`raw_header` 保留原始多层表头拼接文本。规范化期间仅用于比较和分组，不能覆盖原始表头。年初与上年末可以形成明确的比较关系，但必须保存各自原始表头；调整前、调整后或数值不同的列不得合并。

### 非金额列

表级元数据新增 `non_amount_columns`。每项包含 `block_id`、绝对 `column`、`header_rows`、`raw_header`、`kind` 和表头证据。`kind` 仅允许 `note_reference`、`sequence` 或 `other`。

Python 使用这些声明区分附注编号、序号与金额列。声明为非金额列不表示可以忽略整个列：其表头和坐标必须与 Markdown 一致；未声明且包含可解析金额的列仍报告 `unmapped_numeric_column`。

### 行和数值

Agnes 对每行返回原始科目名、物理表、行坐标、可选标准概念和每个金额的绝对列坐标。未知科目保留 `concept=null`、原名及原值，不强制标准化。标准概念只覆盖七条公式和现有最小展示兼容所需科目。

系统提示统一明确：不计算、不补零、不推导、不跨单元格拼数、不为了满足公式修改数字。模型返回的 `raw_value` 只用于交叉核验，落库原值始终从指定 Markdown 单元格读取。

## 确定性来源校验

Python 对每个候选执行以下检查：

1. `block_id`、行、列定位到唯一 Markdown 单元格。
2. 原始科目名与 `label_column` 对应单元格一致。
3. 模型抄录数字与金额单元格一致；最终 `raw_value` 从该单元格读取。
4. 金额列坐标属于声明的期间列，表头证据与完整期间一致。
5. 单位、币种、主体和口径均有允许范围内的逐字原文证据。
6. 通过后才用 `Decimal` 和已核实单位换算；保留原始小数位数作为披露精度。

无法可靠定位或元数据缺证据的值标记为待核对，不猜填。来源状态与公式状态完全分离；任何公式结果均不得改变 `raw_value`、`normalized_value` 或来源验证状态。

### 期间规则

期间解析必须依据完整表头和证据，不得只比较年份：

- “2025 年 1—3 月”“2025 年第一季度”和明确的 1 月 1 日至 3 月 31 日累计区间属于季度累计口径。
- 单季口径只有原文明确为“本季度”“7—9 月”等非年初起算区间时成立。
- “1—6 月”“半年度”属于半年累计，不得归为二季度单季。
- 流量表必须记录起止期间；时点表必须记录时点。
- 年初数与上年末仅在来源明确且值一致时允许建立等价分组；两列原始表头仍分别保留。
- “调整前”“调整后”等修饰语进入列身份，禁止仅凭规范化日期合并。

### 本地旧规则

本地解析器继续作为第二意见，只能生成诊断，例如提示 Agnes 可能漏表、漏列或口径冲突。它不能覆盖 Agnes 坐标，也不能把自己的值升级为来源已核实结果。

## 七条财务恒等式

检查器固定实现以下关系：

1. 资产总计 = 负债合计 + 所有者权益合计。
2. 流动资产合计 + 非流动资产合计 = 资产总计。
3. 流动负债合计 + 非流动负债合计 = 负债合计。
4. 利润总额 − 所得税费用 = 净利润。
5. 营业利润 + 营业外收入 − 营业外支出 = 利润总额。
6. 经营活动净现金流 + 投资活动净现金流 + 筹资活动净现金流 + 汇率影响 = 现金及现金等价物净增加额。
7. 期初现金及现金等价物 + 现金及现金等价物净增加额 = 期末现金及现金等价物。

每次检查只使用同一逻辑表、主体、口径、期间、币种、单位且来源已核实、标准映射确定的披露值。重复概念或不确定映射不能作为公式输入。

每条检查返回：`code`、`status`、`difference`、`tolerance`、`missing_concepts`、`involved_concepts`、对应项目 ID，以及主体、口径、期间和币种。状态为：

- `passed`：输入完整且差额在容差内。
- `conflict`：输入完整且差额超过容差。
- `not_checked_missing_disclosure`：缺少披露项，未检查。
- `not_checked_unverified_source`：存在候选输入，但来源或映射未核实。

缺项不补零，不因 `not_checked_missing_disclosure` 触发复查。公式冲突保留全部来源已核实数值，只向相关逻辑表和涉及项目添加公式报警，不影响无关科目。

### 舍入容差

每个输入保留源单元格的小数位数。按其原币原单位的最后一位披露精度计算半单位误差，再按已核实单位换算到统一计算单位。公式总容差为所有输入项半单位误差的绝对值之和；公式两边所有披露项都计入，不使用固定百分比或固定 `0.02 × unit`。

## 一次定向复查

初次完整来源校验和公式检查后，系统按逻辑表汇总问题。满足以下任一条件才触发复查：存在来源定位/抄录/列期间/单位/主体/口径问题，或存在 `conflict` 公式。单纯缺少披露项不触发复查。

每张逻辑表最多一轮语义复查。复查请求包含原表所有相关分片、原元数据和行提取结果、来源问题、公式差额、容差及涉及科目。Agnes 可返回完整修订后的表元数据与相关行，因此可纠正期间、单位、行列定位和相关映射；不得修改不相关的成功行，也不得直接提交计算所得数字。

复查结果替换该逻辑表本轮的候选解释后，Python 重新运行全部来源检查和七条适用公式。仍有来源问题或公式冲突时停止，标记 `manual_review_required`，不进行第二轮语义复查。

复查沿用现有模型调用、分片、租约、阶段缓存和共享限流。网络请求自身的最多三次传输尝试与“每张逻辑表最多一次语义复查”分别计数。所有实际请求，包括重试和复查，继续受默认 18 次/分钟、硬上限 20 次/分钟约束。运行清单记录 `semantic_review_count`，取值只能为 0 或 1。

## 持久化、接口与网页

检查结果和复查摘要保存在现有 `ExtractionRun.manifest`；报表接口从当前批次清单返回对应检查，不创建新的修订实体或审批接口。历史识别批次继续不可变，新识别产生新批次。

现有财务报表结果接口为每张逻辑表返回：

- `source_status`：来源是否全部一致及问题列表。
- `formula_status`：`passed`、`warning`、`not_checked` 或 `mixed`。
- `checks`：七条中适用于该表的检查明细。
- `semantic_review_count` 与 `manual_review_required`。

网页原表区域优先显示 `source_name`，未知标准科目正常出现。每张报表顶部仅增加简短状态提示，例如“资产负债表勾稽不一致”；点击后展示差额、容差、缺项、相关科目和各自来源。来源待核对与公式不一致使用不同文案和样式。现有指标只做字段兼容，不扩展指标功能。

## 自动回归

自动测试至少覆盖：

- 错误行列坐标、数字抄录不一致和科目单元格不一致。
- 中文 1—3 月、单季度、半年累计、完整年度和时点期间，防止只按年份匹配。
- 年初/上年末保留原表头，调整前后和不同数值不合并。
- 单位与币种证据误读以及 `Decimal` 换算。
- 附注编号/序号列不计为遗漏金额，未声明的真实金额列仍报警。
- 未知科目保留原名和数值，但不以不确定映射参加公式。
- 七条公式的通过、冲突、缺披露项、来源未核实和逐项披露精度容差。
- 公式冲突不清空数值、不改变来源状态、不污染无关科目。
- 来源问题或公式冲突触发一次复查；只有缺项不触发；复查后仍失败即停止并要求人工核对。
- 网络重试与语义复查分别计数，复查仍受共享限流和断点机制约束。
- API 字段和网页状态详情，以及既有财务视图兼容。

## 六家公司真实 PDF 验收

首轮选择六家非金融上市公司，每家公司一份公开 PDF，其中三份年报、三份半年报。样本应包含跨页表、多层表头和不同金额单位等明显排版差异。样本清单记录公开下载地址、文件摘要、报告类型和选择理由；PDF 固定后，在运行 LeaseDD 前预先确定抽样科目。

每家公司检查：三张表是否找全，合并与母公司是否分开；总资产、总负债、净资产、营业收入、营业成本、净利润及三类活动净现金流；并从每张表预先随机抽取五个普通科目，共十五项，核对其全部期间列。

普通 CSV 对照表固定包含：公司、PDF 页码、科目、期间、PDF 原值、LeaseDD 值、结果、失败原因。缺失和待核对均不计为正确。失败原因仅使用转换、找表、期间、列、单位、主体或科目七类之一，并可附简短说明。任何错误数字被标为来源通过都必须单独记录并修复通用原因。

人工逐项查看原 PDF，不能用企业预警通或其他数据库代替。自动 Markdown 来源校验与人工 PDF 抽查在验收报告中分开统计。若六家公司暴露新的通用版式问题，可扩展到最多十家；只修通用问题，不建设新的 benchmark 系统。

## 交付与完成标准

交付物包括：可运行版本、自动回归结果、六家公司实际运行结果、PDF 对照 CSV、样本清单及剩余问题清单。验收必须证明三表找全和规定抽查项逐项有记录；任何跳过、缺失或待核对均明确列为未通过。

对外结论仅描述这些样本的表现，不宣称支持任意公司或任意 PDF。未完成人工 PDF 抽查前，不能把自动校验称为人工确认，也不能将本阶段标记完成。
